# Issues #125, #170, #145, #143: Implementation Notes

## #125: Optimistic appointment cancellation with rollback

**Files:** `src/services/appointmentMutations.ts`, `src/components/appointments/UpcomingAppointments.tsx`

`useCancelAppointmentMutation({ queryKey, onOptimisticCancel, onRollback, onCancelled })` holds the
TanStack Query lifecycle. Any list that caches `Appointment[]` can reuse it.

| Phase       | Behaviour                                                                                                                                                                                                                                                                                     |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `onMutate`  | `cancelQueries` stops in-flight refetches. It snapshots the cached list and the appointment's previous status, marks the appointment `cancelled`, and the component switches to the **Canceled** tab before the request is sent.                                                              |
| `onError`   | Restores **only the failed appointment** from the snapshot (`rollbackAppointmentCancellation`). A second cancellation that is still pending keeps its optimistic state. The toast explains why it failed (`describeCancellationError`: network, 409, 401/403, 404, 5xx) and offers **Retry**. |
| `onSettled` | Refetches once the _last_ concurrent cancellation settles (`isMutating({ mutationKey }) <= 1`). An earlier refetch could overwrite another optimistic update.                                                                                                                                 |

## #170: Sentry distributed tracing and PII masking

**Files:** `src/lib/sentry.ts`, `sentry.{client,server,edge}.config.ts`, `src/lib/stellar.ts`

All three runtimes call `Sentry.init(getSentryOptions(runtime))`, so they share one policy.

**Tracing**

- `traceUserAction(name, fn)` starts a `ui.action` transaction. Axios (XHR) requests made inside it become child
  spans and carry `sentry-trace`/`baggage` to the backend. The trace runs click → API → backend.
- `invokeSorobanContract` is wrapped in `traceStellarTransaction`: one `stellar.tx` span with `stellar.tx.build`,
  `.simulate`, `.sign`, `.submit` and `.confirm` children, and `stellar.tx_hash` set once known. Wallet signing time and RPC
  submission or confirmation latency show up separately.
- `callHorizonWithFallback` runs inside a `stellar.horizon` span that records the endpoint that answered and the
  number of failover attempts.
- Trace headers go only to same-origin URLs and to the `NEXT_PUBLIC_API_URL` origin. Horizon, Soroban RPC and
  anchors still get timed `http.client` spans, but no custom headers, which would force CORS preflights they may reject.

**Sampling ("zero performance degradation")**

- The `tracesSampler` honours the parent decision first, so distributed traces are never cut in half.
- Health checks, static assets and images are never traced.
- Production defaults: 10% base, 50% for `stellar.*` lifecycles (rare, user-initiated, high value) and 10% replay
  sessions. All three can be overridden with `NEXT_PUBLIC_SENTRY_*_SAMPLE_RATE`.
- `enabled` also needs a DSN, so builds without monitoring do no instrumentation work.

**PII masking**: `beforeBreadcrumb`, `beforeSend` and `beforeSendTransaction` run `scrubBreadcrumb`/`scrubEvent`:

- Values under keys that look like diagnoses, notes, ICD codes, prescriptions, intake data, names, emails, phones,
  addresses, licenses, tokens, signatures, seeds, mnemonics, private keys and similar are masked.
- In free text, Stellar secret seeds (`S…`), account and contract addresses, Bearer tokens, JWTs, emails and long base64
  blobs (signed XDR, ciphertext) are redacted.
- Query strings are dropped from URLs, breadcrumbs and span descriptions. Request bodies, cookies and console
  breadcrumb arguments are dropped as well.
- `user` keeps only the pseudonymous `id` set by `setSentryUser`. `sendDefaultPii` is `false`, and replays mask all
  text and inputs and block media.

## #145: Admin role verification queue

**Files:** `src/components/auth/RoleVerificationQueue.tsx`, `src/lib/roleVerification.ts`,
`src/app/dashboard/admin/page.tsx` (Pending Approvals tab), `src/middleware.ts` (`frame-src blob:`)

- **Split screen:** applicant profile and license metadata (with expiry warnings) on the left. The uploaded
  credentials are on the right, in a PDF viewer with document tabs.
- **Credential handling:** files are downloaded as Blobs through the authenticated API (never public URLs). They are
  checked for `%PDF-` magic bytes and rendered from a `blob:` URL that is revoked on change. They are not kept in the
  query cache (`gcTime: 0`).
- **Approve:** the admin's wallet signs `grant_role(admin, applicant, role)` on
  `NEXT_PUBLIC_ACCESS_CONTROL_CONTRACT_ID` (traced as `soroban.grant_role`). Then the decision is recorded with
  `grantTxHash`. If recording fails after the grant confirmed, the tx hash is kept and **Retry** does not ask for a second
  signature.
- **Reject:** requires one of the standardized `REJECTION_REASONS`, plus a note of at least 10 characters for `OTHER`.
- **Notification email:** the backend's decision endpoint sends it in the same request. The UI shows
  `queued`/`sent`/`failed` and can **Resend**. Email is never sent from the browser.

## #143: Schedule templates with seasonal overrides

**Files:** `src/lib/scheduleTemplates.ts`, `src/components/doctor/ScheduleTemplateBuilder.tsx`,
`src/components/doctor/ScheduleOverridePicker.tsx`, `src/app/dashboard/doctor/page.tsx`

- **Templates:** create from presets (_Standard Clinic Week_, _Surgery Week_, _Vacation_) or start blank. Rename,
  set the slot length, delete, and pick the **active** template with a radio toggle. Templates and overrides save through
  `PUT /doctors/schedule-templates` with an optimistic-concurrency `version`.
- **Drag and drop builder:** a Monday to Sunday, 06:00 to 22:00 grid with 30-minute snapping, using native HTML5 drag and drop
  (no new dependency). Drag 1 h, 2 h or 4 h blocks from the palette to create hours, or drag a block to move it. Overlapping
  or touching blocks merge. A focused block can also be moved with the arrow keys, removed with Delete, and resized with −/+.
- **Overrides:** a date picker for holidays and clinical conference leave (day off), or custom hours for that date.
  An override always wins over the template.
- **Slot generation:** `generateSlots` expands the active template over 1 to 12 weeks. It applies overrides and the doctor's
  availability buffer, skips past times, and builds each slot from calendar fields so DST is handled. Slot ids are
  deterministic (`doctorAddress:ISO start`).
- **Atomic bulk publish:** a local pre-check against existing slots and booked appointments fails fast. Then one
  `POST /doctors/slots/bulk` with `atomic: true` and an `Idempotency-Key`, reused across retries of the same slot set
  because axios-retry re-sends POSTs on network errors. A `409 { conflicts }` means nothing was written, and the conflicts
  are listed. Published slots (up to 100) go to the existing `SlotBatchPublisher` for on-chain initialization.
